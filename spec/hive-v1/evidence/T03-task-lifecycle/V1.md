## Observation: a large record exceeds the store read cap

This observation is outside the task behavior and is a shared-store gap. The
store reader caps a record at 1 MiB (`maxRecordSize`). The store writer has no
size check. A direct call with a value above the cap therefore returns `ok` and
writes a record that no read can read.

Reproduction: a temporary test in `internal/task` called `Create` with a
2 MiB title and an explicit 40-character slug, and called `Verify` with a 2 MiB
reason. The command and output:


A later `task list` also fails, because `listInUnlocked` reads the same record.
One oversized record therefore hides every other task in the list.

The gap is latent through the documented CLI. On Linux the kernel caps one
argument at 131072 bytes, so a title, a dependency list, or a reason from the
command line cannot reach 1 MiB in one record. The gap needs the store writer to
reject a record above the read cap before the write. T03 does not edit the
store and does not add a title limit.
