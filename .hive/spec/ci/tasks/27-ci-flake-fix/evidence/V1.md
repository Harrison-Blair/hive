## Findings

### TUI race

Run `39313104438` failed `TestRunHomeReportsInputFailure`. The race report names `Program.shutdown.1` at Bubble Tea `tea.go:1304` as the reader and `Program.startRenderer` at `tea.go:1449` as the writer. Hive's old `internal/tui/tui.go:333-339` called `program.Kill()` from a fault goroutine while `program.Run()` started in another goroutine. `Kill` can start shutdown before renderer startup finishes. This is a real data race.

The code now calls `program.Quit()`. `Quit` sends a quit message. The program handles the message in its event loop and then shuts down. The input failure remains returned by `RunHome`.

### Inbox append lock timeout

Run `39311856837` failed at `internal/lib/inbox/inbox_test.go:200` with `store lock timeout`. The test launches ten writers, checks that all 50 appends succeed, and checks record count and unique sequence numbers. It does not check speed. Old `internal/lib/inbox/inbox.go:73` passed `context.Background()` to `WithLock`. Old `internal/lib/store/lock.go:21` set the default wait to two seconds, and `lock.go:74-78` used that bound when the context had no deadline. Race instrumentation and disk contention made a correct append wait longer than that bound.

`Append` now gives lock acquisition a ten-second context deadline. The test still checks all records and sequence numbers. This longer wait has no speed assertion; it bounds how long an append waits for the shared store lock.

### Supervisor watcher shutdown

Run `39311829750` failed at `internal/supervise/watch_test.go:98`: `stop did not arrive within one second`. Old `internal/supervise/watch.go:94` used a blocking `syscall.Read`. Old `watch.go:151-155` closed the `done` channel and the file descriptor, but it did not wait for the reader goroutine. A close from another goroutine does not reliably interrupt a blocked read. The test started and stopped a supervisor on each iteration, so the reader goroutines could remain blocked across iterations.

A pre-fix diagnostic run with a five-second wait captured the reader blocked in `syscall.Read` at `watch.go:95`; the supervisor loop was still waiting at `supervise.go:251`. The stack excerpt was captured by this command:

```sh
taskset -c 0 go test -race -count=20 -cpu=2 ./internal/supervise/ -run TestWatchFinishedMarkReachesStop
```

```text
goroutine 18 [syscall]:
  syscall.Read(...)
  github.com/Harrison-Blair/hive/internal/supervise.(*watcher).read(...)
      internal/supervise/watch.go:95
  created by github.com/Harrison-Blair/hive/internal/supervise.newWatcher
      internal/supervise/watch.go:48
goroutine 14 [select]:
  github.com/Harrison-Blair/hive/internal/supervise.(*Supervisor).loop(...)
      internal/supervise/supervise.go:251
```

The watcher now uses a nonblocking descriptor. Its reader checks `done`, waits on a short ticker after `EAGAIN`, and exits on close. `Close` waits for that reader before it closes the descriptor. This stops reader goroutine leaks. The test keeps its original one-second correctness check.

### Grouped store lock timeout

Run `39309318840` failed at `internal/lib/store/grouped_test.go:54` with `store lock timeout`. The test checks that each grouped read sees equal versions while a writer updates both records. Old lines `27` and `40` used `WithLock(context.Background())`; old `internal/lib/store/lock.go:21,74-78` limited each lock wait to two seconds. The test checks consistency, not lock acquisition speed.

The test now gives each lock operation a ten-second deadline. It keeps the same 200 rounds and version-equality assertion. The per-operation timeout allows race-instrumented scheduling time; it does not add a speed requirement.
