The field for wave 5 is `Trust.NoMethod` (`internal/lib/harness/harness.go`).
A non-empty value is the reason that no method exists. `Trust.Args` go after
the profile start arguments. `Trust.Env` holds `KEY=VALUE` pairs for the
environment of the harness process (for example `herdr tab create --env`).
`Trust.Version` is the tested version. The trust method is not part of
`Profile.Args()`, so the start of a worker or a verifier does not change.

## Location of the test directory

The brief asks for a new empty directory under `.hive/tmp/` of the worktree.
That directory is below `/home/penguin/source/hive`. Claude Code
(`~/.claude.json`), Codex (`~/.codex/config.toml`), and Pi
(`~/.pi/agent/trust.json`) already trust that path. A first probe of
`claude --dangerously-skip-permissions` in `.hive/tmp/` showed no dialog with no
method. So a run in `.hive/tmp/` alone cannot prove a method. Each method ran
in two places: `.hive/tmp/` of the worktree, and `/tmp/claude-1000/hive-trust/`,
which no harness trusts. The runs with no method in `/tmp/claude-1000/hive-trust/`
show the dialog, so the method is the cause of each clean start.

## How each method was found

- claude: the trust check in the 2.1.307 binary returns true when
  `CLAUDE_CODE_SANDBOXED` is set, before it reads `~/.claude.json`. The value
  holds only in the process. After a run with the value, `~/.claude.json` had
  no record for the directory, and a second start in the same directory with
  no value showed the dialog again. `--settings` cannot set
  `hasTrustDialogAccepted`. This variable is not in `claude --help`; a new
  Claude Code version can change it.
- codex: a new directory that is not a Git repository shows no trust dialog.
  After `git init`, the folder dialog shows ("Your trust decision will be
  saved"), also with `--dangerously-bypass-approvals-and-sandbox`.
  `-c 'projects."DIR".trust_level="trusted"'` did not skip it, with and without
  a dot in the path; Codex reads folder trust only from the user config. The
  methods that remain are rejected: a saved `trust_level = "trusted"` in
  `~/.codex/config.toml` trusts the directory for all time and changes a
  global config. A preflight that starts Codex with a copied `CODEX_HOME`
  splits the sessions and the auth token refresh from the user home.
  `~/.codex/config.toml` did not change in any run.
- cursor: `--trust` skips the dialog. It writes
  `~/.cursor/projects/<slug>/.workspace-trusted` with
  `"trustMethod": "cli-flag"`. A second start in the same directory with no
  flag showed no dialog, so the trust stays for all time. The 2026.10.19 bundle
  reads trust only from that marker or a config list; it has no per-run
  override. The probe markers and chat folders were removed after the check.
- opencode: a new directory shows no dialog.
- pi: Pi shows the project trust dialog only when the directory has
  project-local resources, for example `.pi/settings.json`. `--approve`
  ("Trust project-local files for this run") skips it. `~/.pi/agent/trust.json`
  did not change.

## Other dialogs (not trust of the directory)

- codex 0.160.1 shows "Update available · 0.160.1 → 0.163.0" before each other
  screen (run `codex-nogit` below). With `-c check_for_update_on_startup=false`
  it next shows "Hooks need review: 2 hooks are new or changed". These come
  from the user config and hooks, not from the directory. The profile comment
  already lists the hook dialog. The `codex-git` run used
  `-c check_for_update_on_startup=false --dangerously-bypass-hook-trust` only to
  reach the folder dialog. Neither flag is in the profile.
- cursor auto-updated from 2026.09.18-9a7762b to 2026.10.19-6bbf2c4 during the
  check. The first `--trust` probe ran on 2026.09.18. The persistence check and
  the V1 run below ran on 2026.10.19.

## Result

Each harness with a method (claude, opencode, pi) started with no trust dialog
in a new empty directory, in `.hive/tmp/` of the worktree and in an untrusted
directory. The same claude and pi starts with no method showed the dialog. Each
tab was closed and each directory was removed. Codex and cursor have the result
"no method", with the reason in `Trust.NoMethod`.
