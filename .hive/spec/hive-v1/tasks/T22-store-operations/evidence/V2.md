### Source change

`writeRecordFile` now checks the encoded data length first. The check uses the
existing `maxRecordSize` value of 1048576 bytes. It runs before `atomicWrite`.
A record above the limit gets `record too large: <path>`. The writer does not
truncate the data, does not replace the old record, and does not make a new
record.

```go
func writeRecordFile(path string, data []byte) error {
	if len(data) > maxRecordSize {
		return fmt.Errorf("record too large: %s", path)
	}
	if !validObject(data) {
		return fmt.Errorf("record invalid: %s", path)
	}
	return atomicWrite(path, data)
}
```

The legacy `Write` and `Update` paths, the generic `WriteIn` and `UpdateIn`
paths, and the `LockedStore` methods all call `writePath`. `writePath` is the
only caller of `writeRecordFile`. `writeRecordFile` is the only caller of
`atomicWrite`.

### Covered behavior

- An encoded record of 1048575 bytes and one of 1048576 bytes roundtrip
  through `Write` and `WriteIn`. The final newline is in the count.
- An encoded record of 1048577 bytes and one of 2097152 bytes fail through
  `Write`, `Update`, `WriteIn`, `UpdateIn`, and the held write and update paths.
- A rejected create leaves no record at the path.
- A rejected replacement keeps the old bytes. The old record stays readable.
- A failure of a later write in one group keeps the earlier completed record.
- The escape and UTF-8 case counts one control byte as the six encoded bytes
  `\u0001` and one UTF-8 rune as two bytes. The exact 1048576-byte record
  roundtrips. One added byte fails and keeps the old bytes.
- The test uses no production size constant. It uses no automatic rollback and
  no journal. It changes no title limit. It does not fix a file that is already
  too large.
